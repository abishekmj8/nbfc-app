# ADR-007: Aadhaar & PAN Handling Rules

**Status**: accepted
**Date**: 2026-10-24

## Context

Aadhaar and PAN are the two primary identity documents used in NBFC operations. Both have strict legal rules about collection, storage, verification, display, and sharing. Violations carry heavy penalties. The software must enforce these rules at the architecture level, not leave them to user discipline.

---

## AADHAAR RULES

### Who governs: UIDAI (Unique Identification Authority of India) + RBI KYC Master Directions

### Rule 1: You CANNOT store the full Aadhaar number in your database

**This is a hard prohibition.** The 12-digit Aadhaar number must NOT be stored in any regular database table.

**What to store instead:**
- **Reference token** — a one-way hash (UID token) returned by UIDAI after authentication. This is NBFC-specific and cannot be reverse-engineered to the Aadhaar number.
- **Aadhaar Data Vault** — if the full number MUST be stored (for re-verification or regulatory requirement), it goes in an encrypted, access-controlled **Aadhaar Data Vault** as mandated by UIDAI.

**Implementation in our app:**
```
customer table:
  aadhaar_reference_token  — UID token (stored normally)
  aadhaar_vault_id         — pointer to the Aadhaar Data Vault entry
  aadhaar_last_four        — last 4 digits only (for display/search)
  aadhaar_verified          — boolean
  aadhaar_verified_at       — timestamp
  aadhaar_verification_mode — OTP | BIOMETRIC | OFFLINE_XML | QR

aadhaar_vault table (encrypted at rest, separate access controls):
  id
  encrypted_aadhaar_number  — AES-256 encrypted
  created_at
  accessed_by_log          — every access is logged
```

### Rule 2: Always display Aadhaar as masked

- UI must show: `xxxx-xxxx-1234` (only last 4 digits visible)
- Full Aadhaar is NEVER displayed on screen, in reports, or in exports
- Even in admin views — masked only
- Exception: Aadhaar Data Vault admin with explicit audit-logged access

### Rule 3: Virtual ID (VID) must be supported

- VID is a 16-digit temporary number generated by the Aadhaar holder
- Can be used in place of Aadhaar for authentication
- VID is temporary — **must be deleted after each authentication cycle**
- Never stored permanently

### Rule 4: eKYC verification modes

The app must support multiple Aadhaar verification methods:

| Mode | How it works | When to use |
|---|---|---|
| **OTP-based eKYC** | Aadhaar-linked mobile gets OTP | Remote/digital onboarding |
| **Biometric eKYC** | Fingerprint/iris via certified device | Branch walk-in |
| **Offline XML** | Customer downloads XML from UIDAI, uploads | When online auth is down |
| **QR Code** | Scan QR from Aadhaar card/mAadhaar | Quick branch verification |
| **Digilocker** | Fetch verified Aadhaar from Digilocker | Digital-first workflows |

**OTP-based eKYC restrictions (RBI NBFC Directions 2025, Para 25):**
- Accounts opened via Aadhaar OTP eKYC in non-face-to-face mode have 9 conditions:
  - Balance/deposit limits may apply
  - Must be upgraded to full KYC within a prescribed period
  - App must track and enforce these conditions

### Rule 5: eKYC data retention

- eKYC response data (name, address, photo from UIDAI) can be retained only as long as the customer relationship exists + legal retention period
- Must be deleted/anonymized after that
- Access to eKYC data must be logged

### Rule 6: Consent

- **Explicit consent** required before Aadhaar authentication
- Consent must state the specific purpose
- Consent log: who consented, when, for what purpose, via which mode
- Must support consent withdrawal

### Penalties for violation

- Up to **Rs 1 crore per contravention** for entities violating UIDAI directions
- Continuing failures: additional daily penalties
- Criminal penalties under Aadhaar Act for unauthorized storage/sharing

## PAN RULES

### Who governs: Income Tax Department (CBDT) + RBI KYC Directions

### Rule 1: When PAN is mandatory for NBFCs

PAN must be collected and verified for:

| Transaction | Threshold |
|---|---|
| Loan disbursement | **All loans > Rs 50,000** |
| Cash deposit (single) | > Rs 50,000 |
| Cash transactions (aggregate in a year) | > Rs 10,00,000 |
| Fixed deposit / time deposit | > Rs 50,000 or > Rs 5,00,000/year aggregate |
| Any financial transaction | > Rs 2,50,000 (as per Rule 114B) |
| Opening any account | Always recommended |

**If customer does not have PAN:** Collect **Form 60** (declaration of no PAN) with Aadhaar. The app must support Form 60 capture and storage.

### Rule 2: PAN verification is mandatory (not just collection)

- Collecting a PAN number is not enough — it must be **verified** against the Income Tax database
- Verification via **NSDL/Protean PAN Verification API** or **UTIITSL API**
- Verify: PAN number + Name + Date of Birth match
- Check PAN status: Active, Inactive, Deactivated, Fake
- **Do not proceed with a loan if PAN is inactive or deactivated**

**Implementation:**
```
customer table:
  pan_number              — stored (PAN is not restricted like Aadhaar)
  pan_encrypted           — AES-256 encrypted version for storage
  pan_masked              — "XXXXX1234X" (show only last 4 + check digit)
  pan_verified            — boolean
  pan_verified_at         — timestamp
  pan_status              — ACTIVE | INACTIVE | DEACTIVATED | NOT_FOUND
  pan_holder_name         — name as per IT database
  pan_name_match_score    — fuzzy match score with customer name
```

### Rule 3: PAN display and masking

- In UI: show as `XXXXX1234X` (mask first 5 characters)
- Full PAN visible only to authorized roles with audit log
- In reports/exports: always masked unless regulatory report requires full PAN
- In printed documents (loan agreement, KFS): masked

### Rule 4: PAN-Aadhaar linking

- As of current rules, PAN must be linked with Aadhaar
- Unlinked PAN becomes **inoperative** (cannot be used for transactions)
- App should check PAN-Aadhaar link status during verification
- Alert if customer's PAN is inoperative

### Rule 5: PAN for entities (non-individuals)

- Companies, partnerships, trusts have PAN too
- For MSME/business loans: collect PAN of the entity AND the authorized signatories
- Verify entity PAN status separately

### Rule 6: Form 60 (no PAN declaration)

When a customer genuinely does not have PAN:
- Collect **Form 60** — declaration under Rule 114B
- Form 60 requires: name, address, Aadhaar number, reason for no PAN
- Store Form 60 as a document
- Flag the account as "Form 60 — no PAN"
- Follow up for PAN once obtained

## COMBINED RULES (BOTH AADHAAR + PAN)

### Storage Security
| Field | Storage | Display | Who can see full |
|---|---|---|---|
| Aadhaar | Encrypted Data Vault only | `xxxx-xxxx-1234` | Nobody in normal operation |
| PAN | Encrypted field in DB | `XXXXX1234X` | Authorized role + audit log |
| Bank account | Encrypted field in DB | `XXXXXXXX1234` | Authorized role + audit log |

### Access Logging
- **Every access** to Aadhaar (even masked) must be logged
- **Every access** to full PAN must be logged
- Log: who accessed, when, from which IP, for what purpose
- These logs are part of the audit trail and cannot be deleted

### API Integration Points
```
Aadhaar:
  - UIDAI eKYC API (via KUA/ASA) — for OTP/biometric verification
  - Aadhaar Offline XML — for offline verification
  - Digilocker API — for document fetch

PAN:
  - NSDL/Protean PAN Verification API — verify PAN details
  - Income Tax e-filing portal — PAN-Aadhaar link status
  - NSDL PAN Status API — check active/inactive

Both:
  - CKYC (Central KYC Registry) — upload/fetch KYC records
  - Credit Bureau APIs — need PAN for credit pull
```

### Data Retention
| Data | Minimum retention | Maximum retention | After expiry |
|---|---|---|---|
| Aadhaar (vault) | Duration of relationship | + 5 years (PMLA) | Delete from vault |
| Aadhaar eKYC data | Duration of relationship | + 5 years (PMLA) | Delete/anonymize |
| PAN | Duration of relationship | + 8 years (IT Act) | Delete/anonymize |
| KYC documents | Duration of relationship | + 5 years (PMLA) | Delete |
| Consent logs | Duration of relationship | + 5 years | Archive |
| Verification logs | Duration of relationship | + 8 years | Archive |

## Consequences for the Software

### Architecture requirements:
1. **Aadhaar Data Vault** — separate encrypted table with its own access controls, never joined with regular queries
2. **Field-level encryption** — PAN, bank account encrypted at the application layer (not just DB-level)
3. **Masking middleware** — API responses automatically mask PII unless caller has explicit permission
4. **PII access audit** — separate log for every PII field access, not just mutations
5. **Verification status tracking** — every identity document has verified/unverified status with timestamp
6. **Form 60 workflow** — alternative path when PAN is unavailable
7. **KYC expiry engine** — tracks re-verification due dates, sends alerts
8. **Consent management** — per-purpose consent capture and withdrawal for Aadhaar usage
