# ADR-013: Multi-Language / Internationalization (i18n)

**Status**: accepted
**Date**: 2026-10-24

## Context

RBI's Fair Practices Code requires that loan agreements and key documents be provided in the borrower's preferred language. India has 22 scheduled languages and diverse regional NBFCs. The app UI must at minimum support English and Hindi, with the ability to add regional languages. Document generation has stricter language requirements than the UI.

---

## Decision: next-intl with JSON dictionaries

### Library: next-intl

**Why next-intl:**
- Built for Next.js App Router (server components + client components)
- JSON-based dictionaries — easy to add new languages
- Server-side rendering of translations (no flash of untranslated content)
- Supports ICU message format (plurals, numbers, dates)
- Middleware for locale detection (cookie → Accept-Language → default)
- Lightweight, well-maintained

### Why not next-i18next?
- Designed for Pages Router, App Router support is an afterthought
- next-intl is the community standard for App Router

---

## Scope: What Gets Translated

### Tier 1: UI Labels & Messages (Phase 1)
- Navigation, menus, buttons, form labels
- Error messages, validation messages
- Status labels, toast notifications
- Dashboard headings and descriptions

### Tier 2: Document Templates (Phase 1)
- Loan agreement, sanction letter, KFS
- Payment receipts, demand notices, NOC
- These MUST support the borrower's preferred language (RBI FPC requirement)

### Tier 3: Data-Driven Content (Phase 2)
- Loan product names and descriptions
- Fee type names
- Custom fields and labels
- Email/SMS notification templates

## Locale Resolution

Priority order:
1. **User preference** (stored in user profile in DB)
2. **Cookie** (`NEXT_LOCALE` cookie)
3. **Accept-Language header** (browser preference)
4. **Default locale** (`en`)

Middleware in `middleware.ts` handles locale detection and URL routing.

## Number & Currency Formatting

Indian formatting via `Intl.NumberFormat`:

```typescript
// Money (paise to rupees with Indian separators)
formatMoney(15000000) → "₹1,50,000.00"  // English
formatMoney(15000000) → "₹1,50,000.00"  // Hindi (same format, different labels)

// Numbers
formatNumber(1500000) → "15,00,000"      // Indian grouping (lakh, crore)

// Percentages
formatPercent(12.5) → "12.50%"
```

**Rules:**
- Always use Indian numbering system (lakh/crore) regardless of locale
- Rupee symbol (₹) for currency, not "Rs" or "INR"
- 2 decimal places for money, always

---

## Date Formatting

```typescript
formatDate(date, 'en') → "24 Oct 2026"
formatDate(date, 'hi') → "24 अक्तू 2026"

formatDateTime(date, 'en') → "24 Oct 2026, 10:30 AM"
```

- Stored as UTC, displayed in user's timezone
- Timezone configured per branch (a branch in Mumbai = IST, always)
- Default timezone: Asia/Kolkata (IST, UTC+5:30)

## Document Language

Separate from UI language. Documents use the **borrower's preferred language**:

```
Customer record:
  preferredLanguage: "hi"  // Hindi

When generating a loan agreement for this customer:
  → Use Hindi template
  → Hindi fonts loaded
  → Money in words in Hindi: "रुपये एक लाख पचास हज़ार मात्र"
```

**Rules:**
- Borrower's preferred language stored in customer profile
- Document generation uses borrower's language, not the officer's UI language
- If a language template is not available, fall back to English + log a warning
- Bilingual documents (English + regional) supported for legal safety

---

## Right-to-Left (RTL)

Urdu is the only RTL language in our potential scope.

**Decision:** Not in Phase 1 or 2. If Urdu support is needed:
- Tailwind supports RTL via `dir="rtl"` + `rtl:` variant
- shadcn/ui components are RTL-compatible via Radix UI
- Can be added without architectural changes

## Font Strategy

**Google Noto Sans family** — covers all Indian scripts in a consistent style.

| Script | Font | Used for |
|---|---|---|
| Latin | Noto Sans | English, URLs, numbers |
| Devanagari | Noto Sans Devanagari | Hindi, Marathi, Sanskrit |
| Gujarati | Noto Sans Gujarati | Gujarati |
| Bengali | Noto Sans Bengali | Bengali, Assamese |
| Tamil | Noto Sans Tamil | Tamil |
| Telugu | Noto Sans Telugu | Telugu |
| Kannada | Noto Sans Kannada | Kannada |
| Malayalam | Noto Sans Malayalam | Malayalam |
| Gurmukhi | Noto Sans Gurmukhi | Punjabi |

**Loading strategy:**
- UI: Noto Sans Latin loaded always. Regional fonts loaded only for selected locale (dynamic import)
- PDFs: Font files bundled with the app (React-PDF requires font registration)

---

## Translation Workflow

1. Developer adds English key to `en.json`
2. Keys without translations in other locales → show English (fallback)
3. Translation done by NBFC staff or translation service
4. New language = new JSON file + font → no code deployment needed
5. Translation completeness dashboard in Settings → "Hindi: 94% translated"

---

## Consequences

- **Enables**: FPC compliance, regional NBFC adoption, borrower-friendly documents
- **Trade-off**: Phase 1 is English + Hindi only — regional NBFCs may need to wait
- **Trade-off**: Font files add ~200KB per script to the PDF generation bundle
- **Architecture impact**: All user-facing strings go through `t()` function from day one — no hardcoded strings
